# BioQuorum 产品定义

> 状态：草案 v0.1（2026-11-11）
> 名称 **BioQuorum** 是暂定名。PyPI 和 GitHub 上暂无同名项目，商标还没有查。
> 寓意：生物学里的 *quorum sensing*（群体感应），加上"多个模型达成共识（quorum）才算可信"。

---

## 1. 一句话定位

**面向生物医药研究的开源 AI 科研工作台：不绑定模型，结论经过交叉验证，结果可以复现，可以完整部署在你自己的环境里。**

English: *The open, model-neutral AI workbench for biomedical research — cross-verified, reproducible, and private by design.*

## 2. 为什么需要它

| 现状 | 问题 |
|---|---|
| Claude Science 等商业工作台 | 只能用一家的模型；数据要发给厂商；自己检查自己（Reviewer 和主 agent 用同一个模型） |
| 现有开源替代（openscience 等） | 通用功能做得不错，但都是"开源版 Claude Science"的思路。在验证、复现标准、私有化合规这几方面没有做深 |
| 科研人员的真实顾虑 | "AI 给的结论能不能信？""半年后还能重跑出来吗？""公司数据能不能用？" |

BioQuorum 就是要回答这三个问题。

## 3. 目标用户

| 角色 | 需求 | 版本优先级 |
|---|---|---|
| **计算生物学家 / 生信分析师**（主要用户） | 加速组学分析、查数据库、出图，同时代码和过程可追溯 | v0.1 起 |
| **研究平台 / IT 负责人**（部署者） | 能自托管、自己控制模型和成本、有审计、数据不外泄 | v0.5 起 |
| **湿实验科学家 / 药物化学家**（扩展用户） | 不写代码，问靶点、文献、化合物问题，要带引用的可靠回答 | v0.3 起（要有好用的 UI） |

## 4. 三个北极星场景

所有功能都围绕这三个场景设计。它们也是 demo、示例项目和评测集的来源。

**A. 靶点评估档案（Target Dossier）**
> "评估一下 GENE_X 作为 IBD 靶点的潜力。"

依次收集：遗传学证据（Open Targets、GWAS Catalog、gnomAD）、表达谱（GTEx、HPA）、可成药性（ChEMBL、PDB/AlphaFold）、文献、竞争格局（ClinicalTrials.gov）。最后生成一份带引用的报告，每条结论都经过交叉审查。

**B. 组学数据分析（Omics Analysis）**
> "用 GSE_xxxxx 做单细胞 QC、聚类和差异表达，出发表级的图。"

整个过程在常驻 kernel 里执行。每张图都能追溯到生成它的代码、环境和输入数据，并且可以导出成别人能重跑的研究包。

**C. 证据综述（Evidence Review）**
> "化合物 Y 在 Z 疾病里有哪些机制证据？"

检索文献，整理成证据表。每条引用都核实过（DOI 能解析，内容确实支持结论），矛盾的证据会单独标出来。

## 5. 五大支柱

### 支柱 1 · 模型中立（Model-neutral）
- 支持 Anthropic、OpenAI、Google、DeepSeek、Qwen，以及任何 OpenAI 兼容接口（vLLM、Ollama、LM Studio、OpenRouter、LiteLLM Proxy）
- **按角色配置模型**：planner（规划）、worker（执行）、reviewer（审查）、summarizer（压缩上下文），各用各的模型
- 每次调用的 token 和费用都可见，可以设置项目预算
- 失败时自动回退到备用模型

### 支柱 2 · 交叉验证（Cross-verified）
这是**核心差异化**，名字里的 Quorum 就是指这一点。
- Reviewer **默认用和主 agent 不同家族的模型**
- 检查的粒度到每条结论：这个数字真的算过吗？和文件里的一致吗？引用真的支持这句话吗？DOI 指向的是同一篇文章吗？计划里的步骤都做完了吗？
- **可以重跑**：在全新的 kernel 里重新执行关键计算，对比结果
- **共识模式**：重要问题让两个模型各自独立回答，再对比分歧
- 每条结论和每个产物都带验证状态标记：`未验证` → `已审查` → `已复现`

### 支柱 3 · 默认可复现（Reproducible by default）
- 每个产物都有版本，并记录代码、环境锁文件、输入数据的 hash、生成它的对话片段
- 一键重跑任意版本
- **研究包（Research Bundle）是开放格式**，有公开规范（`bundle-spec/`）：不装 BioQuorum 也能看懂、能重跑，可以附在论文后面，也可以交给审稿人
- 自动生成 Methods 段落草稿

### 支柱 4 · 私有优先（Private by design）
- 在本地或自己的服务器上运行，**默认零遥测**
- **项目数据分级**：`public` / `internal` / `confidential`
  - 模型路由强制遵守分级规则，例如 confidential 项目只能用本地模型或白名单里的模型
- 审计日志：每次模型调用（发给了谁、什么分级、多少 token）、每次对外网络访问，都有记录
- 密钥存放在系统钥匙串里，不会出现在模型上下文中

### 支柱 5 · 生物医药深度（Biomedical depth）
- 精选的数据库连接器：质量第一，每个都有测试，并标注数据许可（学术/商用）
- 精选的 Skills 包：组学、靶点、化学信息学、结构生物学
- 专业的查看器：分子（2D/3D）、蛋白结构、基因组轨道、大表格
- 兼容生态：可以导入 Agent Skills（SKILL.md）和任意 MCP 服务器

## 6. 竞品对比

| | Claude Science | openscience 系（3 个开源项目） | **BioQuorum** |
|---|---|---|---|
| 模型 | 只有 Claude | 多模型 | 多模型 + 按角色分配 + 按策略路由 |
| 审查 | 同一个模型自审，不重跑 | 有 reviewer，或者没有 | **跨模型审查 + 可重跑 + 共识模式** |
| 复现 | 只能在应用内使用 | `.science` 包（aipoch） | **开放的研究包规范**，脱离应用也能重跑 |
| 私有化 | 数据发给 Anthropic | 本地运行，部分项目默认上传 trace | 零遥测 + 数据分级路由 + 审计 |
| 领域 | 生物为主，覆盖面广 | 通用科研 | 聚焦生物医药 / 药物研发 |

## 7. 不做什么（v1.0 之前）

- 不做通用编程 agent（那是 opencode / Claude Code 的事）
- 不做湿实验自动化或机器人控制
- 不做临床诊断或决策支持
- 不做多租户 SaaS 托管服务
- 不训练自己的模型
- 不做 HPC 和云算力调度（v1.0 之后再做）

## 8. 产品形态

| 形态 | 说明 | 版本 |
|---|---|---|
| `uvx bioquorum` / `pip install bioquorum` | 启动本地服务，自动打开浏览器 UI | v0.2 |
| CLI | `bq run "..."`、`bq rerun`、`bq export`，可以写进脚本 | v0.1 |
| **MCP Server 模式** | 把科学层（kernel、溯源、连接器）暴露给 Claude Code、opencode、Cursor 等工具使用 | v0.1 |
| Docker 镜像 | 部署到团队服务器 | v0.5 |
| Python SDK | 在代码里调用 | v0.4 |
| 桌面应用（Tauri） | 一键安装 | v1.0 之后 |

## 9. 信息架构

```
Workspace（一次安装 / 一台服务器）
└── Project（项目：数据目录、数据分级、模型策略、Python 环境）
    ├── Sessions（会话：对话、计划、运行记录，可以分叉）
    ├── Artifacts（产物：图、表、报告、数据，带版本和验证状态）
    └── Bundles（导出的研究包）
Library（库）：Skills · Connectors · Specialists（自定义 agent）
Settings（设置）：Models & Roles · Policies · Credentials · Audit Log
```

UI 主布局（三栏）：
```
┌────────────┬──────────────────────────────┬─────────────────────┐
│ 项目/会话   │ 对话流                        │ 产物面板             │
│ 列表        │ · 计划卡片（待批准/进行中）     │ · 图/表/结构查看器    │
│            │ · 代码步骤（可展开看代码与输出） │ · 版本 & 溯源图       │
│            │ · 权限卡片                    │ · 验证状态 & 审查结果  │
│            │ · 审查卡片（发现的问题）        │                     │
│            │ [输入框  @产物  #会话  /skill] │                     │
└────────────┴──────────────────────────────┴─────────────────────┘
```

## 10. "拿得出手"的发布标准

第一次公开宣传（目标 v0.3）之前，必须全部满足：

- [ ] 一条命令装好，5 分钟内跑通示例
- [ ] README 首屏有演示 GIF 或视频，三个北极星场景各有一个示例项目
- [ ] 文档站：快速开始、概念、配置模型、写 Skill / Connector
- [ ] 至少在 3 家模型（含 1 个开源模型）上实测通过，并公布评测结果
- [ ] CI：测试、lint、类型检查全部通过；发布流程自动化
- [ ] `SECURITY.md`（安全模型和限制说明）、`CONTRIBUTING.md`、Apache-2.0 LICENSE
- [ ] 第三方内容的 license 清单（`THIRD_PARTY.md`）

## 11. 成功指标

- **质量**：自建评测集（3 个场景 × 约 30 题）分数，Reviewer 对人工注入错误的召回率
- **复现**：导出的研究包在干净机器上重跑成功的比例
- **采用**：GitHub star、PyPI 下载量、外部贡献的 Connector / Skill 数量
